# БТЭУ ПК — сайт с CMS

Полноценный сайт с собственной админ-панелью (новости, события, программы),
а не статический макет. Публичная часть рендерится на сервере (SSR) из
базы данных; редакторы управляют контентом через `/admin` без доступа к коду.

## Почему так, а не «Wordpress/1С-Битрикс»

Текущий bteu.by работает на WordPress/Elementor — это объясняет тяжёлые
страницы, смешение поддоменов (`i-bteu.by`, `oms.i-bteu.by`, `mentor.bteu.by`)
и разнородный дизайн между разделами. Здесь используется **тонкая
самописная CMS**: у университета несколько плохо связанных между собой
систем именно потому, что для каждой задачи когда-то поставили отдельный
плагин/поддомен. Единая кодовая база и одна БД с самого начала — сознательное
архитектурное решение, а не экономия.

## Стек

- **Node.js 22** (`http`, `node:sqlite`, `crypto` — всё встроено, без `npm install`)
- **SQLite** для контента (новости/события/программы/админы)
- Серверный рендеринг HTML без фронтенд-фреймворка — админка и сайт лёгкие
  и быстрые по умолчанию (SSR, никакой гидратации на клиенте)
- Zero-dependency осознанно: проект должен запускаться сразу, без сетевого
  доступа к npm-реестру. Для продакшена см. раздел ниже — сразу указано, что
  добавить.

## Быстрый старт

```bash
cp .env.example .env
# сгенерировать секрет:
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
# вставить его в SESSION_SECRET в .env, задать ADMIN_BOOTSTRAP_USER/PASSWORD

npm start
# → http://localhost:3000
# → http://localhost:3000/admin (логин из ADMIN_BOOTSTRAP_USER/PASSWORD)
```

При первом запуске автоматически: создаётся `data/bteu.db`, накатывается
`db/schema.sql`, заливается `db/seed.sql` (демо-новости), создаётся первый
админ из `.env`. **Сразу после первого входа удалите `ADMIN_BOOTSTRAP_*` из
`.env`** — иначе пароль лежит на диске открытым текстом.

## Структура проекта

```
src/server.js   — роутинг, статика, security-заголовки, CRUD-эндпоинты
src/db.js       — доступ к БД (единственное место, которое трогать при
                   переходе на PostgreSQL)
src/auth.js     — пароли (scrypt), сессии, CSRF, троттлинг логина
src/render.js   — HTML-шаблоны (публичный сайт + админка)
db/schema.sql   — структура БД
db/seed.sql     — демо-контент
public/         — CSS/JS, отдаются как статика
```

## Что уже сделано «по стандартам»

- **Пароли**: scrypt + соль, сравнение через `timingSafeEqual` (без тайминг-атак)
- **Сессии**: непрозрачный id в cookie (`HttpOnly`, `SameSite=Lax`, `Secure`
  в проде), сами данные сессии — только на сервере
- **CSRF**: токен на каждую форму, привязан к сессии
- **Rate limiting** на `/admin/login` (8 попыток / 15 минут на IP)
- **SQL-инъекции**: везде параметризованные запросы (`node:sqlite` prepared statements)
- **XSS**: все пользовательские строки экранируются при рендере (`esc()`);
  поле "текст новости" осознанно рендерится как HTML для WYSIWYG — см.
  предупреждение ниже
- **Security-заголовки**: CSP, X-Frame-Options, X-Content-Type-Options,
  Referrer-Policy, HSTS в проде
- **Ограничение размера тела запроса** (1 МБ) — защита от тривиального DoS
- **Аудит-лог** действий редакторов (`audit_log`)

## Нюансы, которые нужно закрыть перед реальным запуском

### 1. Это прототип на встроенных модулях — не продакшен-стек как есть
Проект работает без `npm install`, потому что в этой среде нет доступа к
npm-реестру. Это осознанное ограничение демонстрации, а не рекомендация.
Перед реальным запуском:

- **HTTP-фреймворк**: заменить самодельный роутер на Express/Fastify —
  меньше руками написанного кода вокруг парсинга URL и form-data,
  готовые middleware для всего нижеперечисленного.
- **База данных**: SQLite отлично работает для сайта с одним
  write-инстансом (это и есть университетский сайт), но при нескольких
  серверах/подах нужен PostgreSQL — `node:sqlite` меняется только в
  `src/db.js`, остальной код не знает про конкретную БД.
- **Сессии**: сейчас `Map` в памяти процесса — при рестарте сервера все
  редакторы разлогинятся, при нескольких инстансах сессии не расшарены.
  Продакшен: `express-session` + Redis.
- **Валидация форм**: сейчас минимальная (required на фронте + проверка в
  БД по UNIQUE). Добавить `zod`/`joi` на сервере — никогда не доверять
  фронтенду.
- **Загрузка изображений**: сейчас поле "обложка" — просто текстовое поле
  с URL. Реальная загрузка файлов = `multer` + проверка MIME/размера +
  генерация превью (`sharp`, он уже валяется в этой песочнице) + хранение
  вне репозитория (см. пункт про S3 ниже).

### 2. HTTPS и обратный прокси
Node-процесс не должен торчать в интернет напрямую. Стандартная схема:
`nginx` (или Caddy) принимает 443, терминирует TLS (Let's Encrypt/certbot),
проксирует на `127.0.0.1:3000`. Пример `nginx`:

```nginx
server {
  listen 443 ssl http2;
  server_name bteu.by www.bteu.by;
  ssl_certificate     /etc/letsencrypt/live/bteu.by/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/bteu.by/privkey.pem;

  location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
server { listen 80; server_name bteu.by www.bteu.by; return 301 https://$host$request_uri; }
```
Не забыть `TRUST_PROXY=true` в `.env` только после того, как nginx реально
стоит перед приложением — иначе клиент сможет подделать свой IP и обойти
rate-limit на логин.

### 3. Процесс-менеджер и автозапуск
`node src/server.js` не переживёт падение/перезагрузку сервера сам по себе.
Минимум — `systemd`-юнит:

```ini
# /etc/systemd/system/bteu-cms.service
[Unit]
Description=BTEU CMS
After=network.target

[Service]
Type=simple
User=bteu
WorkingDirectory=/srv/bteu-cms
EnvironmentFile=/srv/bteu-cms/.env
ExecStart=/usr/bin/node src/server.js
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
```
Альтернатива — PM2 или контейнер (Docker + любой оркестратор), если
у хостинг-провайдера/Белкоопсоюза принят такой стандарт.

### 4. Резервное копирование
SQLite — это один файл (`data/bteu.db`). Это плюс (проще бэкапить), но
нужна дисциплина:
- ежедневный `sqlite3 bteu.db ".backup backup-$(date +%F).db"` по cron,
  хранить off-site (не на том же диске/сервере);
- перед миграциями схемы — обязательный ручной бэкап;
- при переходе на PostgreSQL — `pg_dump` по расписанию + point-in-time
  recovery, если объём новостей и обращений абитуриентов большой.

### 5. Загруженные файлы и статика
Сейчас `public/uploads/` — просто папка на диске. На проде это узкое
место: при нескольких инстансах приложения файлы должны лежать в общем
хранилище (S3-совместимое, например MinIO на своих серверах — для
госорганизации РБ это может быть требованием) либо раздаваться через CDN.
Изображения на сайт крупные (см. текущий bteu.by — фото по 2-3 МБ без
сжатия) — обязательно генерировать WebP/несколько размеров при загрузке.

### 6. Соответствие законодательству РБ
- **Закон «О защите персональных данных»**: если на сайте появляются формы
  с ФИО/телефоном/email (запись на день открытых дверей, обратная связь),
  нужна политика обработки ПДн (на текущем сайте она есть, её нужно
  перенести и актуализировать) и, вероятно, регистрация оператора ПДн.
- **Реестр СМИ / доменная зона .by**: сайт вуза не СМИ, но проверьте
  актуальные требования Мининформа к доменам .by на момент запуска.
- **Доступная среда**: у текущего сайта есть отдельная страница
  «Доступная среда» — по-хорошему это должна быть не страница, а
  соответствие WCAG 2.1 AA по всему сайту (контраст, навигация с
  клавиатуры, `alt` у изображений, версия для слабовидящих как реальный
  переключатель, а не ссылка на документ). Каркас CSS уже учитывает
  `:focus-visible` и `prefers-reduced-motion`, но полный аудит нужен отдельно.

### 7. SEO и индексация
Добавить перед запуском: `robots.txt`, `sitemap.xml` (генерировать
динамически из таблицы `news`/`pages`), `og:*`/`twitter:*` мета-теги на
уровне `layout()` (сейчас только `description`), канонические URL,
редиректы 301 со старых URL WordPress (`/bteuby/...`, `/news/...`) на новые
— у сайта большая история индексации в Google/Яндексе, её легко потерять
при миграции, если не сохранить старые пути или не настроить редиректы.

### 8. Мониторинг и логи
Сейчас логи — `console.log`/`console.error` в stdout. Минимум для прода:
- ротация логов (`journald` при systemd уже это даёт, либо `logrotate`);
- аптайм-мониторинг (UptimeRobot / собственный Zabbix, раз это госвуз);
- алерт на 5xx-всплеск и на падение процесса.

### 9. Многопользовательская редакция
Роли сейчас — `editor`/`admin` в колонке `admins.role`, но пока не
различаются в коде (любой залогиненный может всё). Перед реальным
использованием несколькими сотрудниками (пресс-служба, приёмная комиссия,
кафедры) — развести права: кто может публиковать, кто только черновики,
кто управляет разделом «Абитуриенту» и т.д. Это уже логика приложения,
не инфраструктуры.

## От прототипа к продакшену — минимальный список пакетов
Если/когда появится доступ к npm-реестру, порядок внедрения:
1. `express` — заменить ручной роутер (низкий риск, механическая замена)
2. `express-session` + `connect-redis` — сессии переживают рестарт
3. `helmet` — те же security-заголовки, но поддерживаемые пакетом
4. `zod` — валидация форм на сервере
5. `multer` + `sharp` — реальная загрузка и оптимизация изображений
6. `pg` + `knex`/`drizzle` — если переходите на PostgreSQL
7. `pino` — структурированные логи вместо `console.log`

Каждый пункт — независимая замена одного модуля, архитектура (`db.js` /
`auth.js` / `render.js` / `server.js`) для этого и разделена.
